## Phase 1 review follow-up

App handoff consent is tied to the plugin's installation ID. Reinstalling requires fresh consent
even when uninstall could not delete the old rows. Updates that keep the handoff permission keep
the installation ID, and the pipeline digest still determines whether a changed pipeline needs
fresh consent.

**Accepted local filesystem race.** ChemDraft rechecks the app and companion identity after
confirmation and immediately before launch. It rejects symlink and reparse-point final components
and gives Windows the exact canonical executable path it verified. macOS launches GUI apps through
`open -a`, which accepts a path. Both platforms still resolve a path when starting the process, so
a local actor with write access to the chosen app's location can replace it between the final
check and the operating system's launch.

## Conductor rulings for Phase 1 (2026-11-23)

These settle the differences above. Where they differ from `docs/plans/send-to-crystal-builder.md`, these win.

1. **Where an arming is created.** Only in Rust, inside `.on_menu_event` for a `plugin.*` menu id, before `emit_menu_command` forwards it, and in the Rust handlers of host-owned boxes (consent, build confirmation, result box). `route_toolset_command` (palettes), `plugin_panel_event_forward`, `plugin_panel_action_forward`, the DOM keydown path, the agent bridge, and the tour's direct invocation never arm. Contributed plugin menu items have no accelerator today, so no keyboard path arms in 1.2.3.
2. **Tool paths.** `invokeAssistantTool` and `invokeRequestTool` (records with `tool: true`) get no `apps` capability at all; a call from them is refused before reaching Rust. There is no SDK self-invocation dispatcher; panel/overlay control routes (`input.source` `panel` / `overlay`) never arm.
3. **Allowance (rule 3).** Match `promptText` as built: a call refused before any host box is shown does not use the arming; once a host box is shown, Cancel consumes it and returns `declined`.
4. **Worker-only (rule 2).** `apps.handoff` plugins register only through the Worker route; in-process registration with `apps.handoff` is refused. Task 1B's "worker and in-process behave the same" applies to every other capability, not this one.
5. **Version bump (1A).** 0.1.28 for handoff in `plugin-api` (`index.ts`, `package.json`) and `plugin-host/package.json`; both equality tests stay green.
6. **Provenance (rule 13, task 1D).** The installed record gains optional `source` (`"catalog" | "sideload"`), `repository` (`owner/name`), and `checksumVerified` (boolean), written by the catalog install and update paths; records without them are treated as sideloaded. The allowlist accepts `source: "catalog"` with a matching repository and `checksumVerified: true` on all builds. Rust also accepts sideloads for allowlisted IDs only under the development bundle identifier `org.chemdraft.desktop.dev` and discloses the exception in the consent box. How Phase 2 tests a pre-release through that path is a Phase 2 question, not Phase 1 scope.
7. **Consent store (rule 5, task 1C).** New file under `<app_local_data_dir>/app-handoff/consents.json` with `schemaVersion: 1`, the same lock / temp-file / rename pattern as `external_tools/consent.rs`, Unix `0600` / dir `0700`. On Windows, owner-only via the crates already in `Cargo.toml` (rule 10: no new dependency); if that is not possible with them, the file lives in the per-user local app-data folder with inherited ACLs and the report says so.
8. **Host boxes that return a choice.** None exists today. Task 1C builds them in Rust with `tauri-plugin-dialog` (`message` with custom buttons) for consent and the loss warning; the build confirmation with a combination choice (1H) uses the shared native dialog host with a new Rust-owned dialog kind whose answer goes to Rust, not to the renderer.
9. **Update with a dropped permission (task 1D).** When the current installed manifest declares `apps.handoff` and the incoming manifest does not, the plugin's handoff consent rows are deleted before the new version registers, and cleanup failure blocks the update. Updates whose current manifest lacks `apps.handoff` do not call the consent store. Uninstall deletes the rows too (same place external-tool consent is cleared).

10. **Authenticate the Worker relay for each native menu invocation (review 2026-11-23).** This amends rule 2's credential-free IPC design. A document-window label and a live menu click identify a window and a gesture. Neither identifies the caller spending that click.

    **Who has document-window IPC.** The main webview runs ChemDraft's renderer and its bundled JavaScript dependencies, including third-party libraries such as React. The renderer imports the bundled mass-fragment registration module. Its handlers normally execute in a module Worker and have a first-party in-process fallback when there is no Worker. The development build also registers ChemDraft's toolset fixture in-process. The packaged-plugin loader always requires a Worker for both official catalog packages and third-party sideloads. Serving the package from ChemDraft's origin permits relative imports. Its entry executes in the Worker's realm, which has no document window or Tauri IPC handle. Plugin panels render declarative reports in host-owned windows (or the inline fallback), and canvas overlays are host-rendered controls. Detached panel windows have their own IPC permissions. The handoff capability grants access only to the main window. Neither surface loads plugin scripts or plugin iframes. A hypothetical unsandboxed same-origin frame with parent access would share the document's trust boundary. The opt-in agent bridge runs first-party code in the main webview. Its callers receive document commands and synthetic input methods. Neither can start a native handoff. MCP and assistant/request tool handlers likewise receive no handoff authority.

    **What Rust binds.** Each eligible native menu click generates a fresh 128-bit OS-random nonce bound to the installed plugin ID and exact command ID. Rust calls an immutable receiver on the main app document directly. Only the bootstrap's private registration closure connects that receiver to the mounted runtime. This gives raw IPC callers no subscription they can claim or replace. The nonce never travels through the DOM event bus, plugin input, a Worker message, or an agent API. The receiver asks Rust to begin the invocation exactly once before running any plugin handler. The host keeps the binding on the active invocation and attaches it to each authenticated Worker capability call. Rust checks all three fields before the picker, consent lookup, submission, file write, or launch. A mismatched caller cannot spend the click or cancel a pending submission. The original expiry, single-spend and authenticated duplicate-submission rules still apply. Completion retires that exact binding, including commands which did no work. Replacement, navigation and shutdown invalidate outstanding menu bindings. Native expiry bounds an unused binding if the finish message is lost.

    **Consent management.** Plugin Manager currently runs in the main webview. Its list and revoke commands therefore share the document's IPC principal. List returns a one-way revocation reference derived from the random picker ID. This reference cannot address an app in a spending request. The invocation check also covers callers that already know a valid picker ID. A caller with main-window IPC can still list consent metadata or revoke access. It also retains the main window's ordinary file and clipboard permissions. This ruling governs the app handoff endpoints.

    **Residual trust.** Rust authenticates possession of the invocation nonce by the trusted host relay. It cannot attest JavaScript code identity inside the same webview. A compromised bundled dependency, same-realm script injection, or a debugger can instrument the first-party bootstrap, host, or Tauri transport to intercept or alter an authenticated call. Such code can also change the selection before the Worker reads it. Defending against that compromise would require an execution boundary outside the main JavaScript realm for the privileged relay. The authorized Worker itself remains responsible for the file contents it submits.
